# Agent Note: 引入 Agent Note 治理层

Status: implemented

## Problem

这个仓库由 agent 大量参与开发，但决策只存在于两个地方：提交信息，以及已经过期的文档。

提交信息能说明"改了什么"，说不清"为什么这样改、当时否掉了什么"。于是同一个问题会被反复重新讨论：为什么 workspace 优先于 chat 作为一级导航、为什么模型配置是个人资源而不是系统资源、为什么 RBAC 缓存放在 Redis 而不是进程内。这些判断在代码里看不见，在提交信息里只有一句话。

`docs/` 承担不了这个职责。它此前每轮开发产出一份执行计划和一份验收记录，累积到 67 个文件、3049 行，最终在 `5aa2afb` 里整体删除。原因是结构性的：这些文档记录的是"某个阶段做了什么"，阶段一过就只剩下与代码不符的陈述。留下的是唯一一份向前看的 `docs/product-roadmap.md`，而它不描述系统当前的样子。

结果是最需要文档的两类读者都没有可用材料：新加入的 agent 无法从文档判断系统现状，只能通读代码；维护者在改动一个跨模块契约时，找不到当初的取舍理由。

## Decision

仓库引入一层轻量治理，只包含三部分：

1. 根目录 `AGENTS.md`：常驻规则，说明约定、何时写决策记录、推送前跑什么检查。
2. `.agents/notes/`：决策记录树，按 `{lifecycle}/{class}` 组织，格式由 gate 强制。规则见 [.agents/notes/README.md](../../README.md)。
3. `scripts/` 下两个 gate，由 `pnpm test:docs` 统一执行：Markdown 相对链接与锚点校验，Agent Note 树结构与格式校验。

扫描范围和笔记类别闭集写在 [scripts/governance-config.ts](../../../../scripts/governance-config.ts)，不在 gate 实现里。

关键约束是"一个事实一个家"：当前行为写在代码里，常驻规则写在 `AGENTS.md`，取舍理由写在 Agent Note，扫描范围写在配置文件。四处互相引用而不重复。笔记只记录仍然成立的判断，代码变了就原地改写；笔记过期就删除，git 历史就是归档。

`implemented/` 笔记禁止出现 `## Proposal`、`## Plan`、`## Acceptance criteria` 这类提案期标题。这正是旧文档失效的根源：验收记录一旦写成"本阶段计划做什么、验收结果如何"，就天然与后续代码脱节。

## Alternatives considered

**继续按阶段写执行计划 + 验收记录。** 已经被这个仓库证伪。67 个文件、3049 行在同一次提交里删除，说明维护成本超过了阅读收益，而且删除时没有任何链接检查能提示影响面。

**只写 `AGENTS.md`，不设 gate。** 成本最低，但每条规则都依赖评审时的注意力。规则一旦无人执行就会退化成传说，而 agent 产出的数量恰恰让注意力成为瓶颈。

**引入完整的 deepseek-harness 治理树。** 包含冻结归档与哈希清单、字数预算、文档引用扫描、禁用词扫描和四个 agent skill。对当前规模来说，每一项都增加维护面，且多数会进入常驻上下文。只保留能机械校验、且直接解决本仓库已发生问题的部分。

**把决策记录写进 `docs/` 而不是独立目录。** `docs/` 已经是产品文档的家，混入决策记录会让两类内容互相稀释；而且 `.agents/` 明确表达了"写给 agent 和维护者看"的受众，与产品文档区分开。

## Consequences

违反规则从"评审时被指出"变成 `pnpm test:docs` 的命令失败，成本前移到提交之前。非平凡改动需要带一条笔记，但机械改动豁免，所以不是每份提交都有文档税。

代价有三点。第一，笔记需要人工判断"是否非平凡"，这条规则本身无法机械校验。第二，常驻上下文新增 `AGENTS.md` 和笔记目录的 README，约 450 tokens。第三，链接 gate 只检查 `[text](path)` 形式的相对链接，反引号里的路径文本检查不到——本仓库此前正是用反引号写了 4 处指向已删除文档的引用，所以那 4 处已改为真正的链接。

被刻意留下的空缺：`.github/workflows/` 没有配置。真实的测试依赖隔离的 MySQL 与 Redis，只跑文档 gate 的 CI 价值有限，因此 gate 挂在根脚本上，并在 `AGENTS.md` 里约定推送前执行。
