# Aura 产品规划文档

## 1. 文档目标

这份文档用于明确 `Aura` 的产品方向，并把当前代码现状转换成可执行的开发路线。

适用场景：

- 作为后续迭代的统一参考
- 作为功能取舍时的判断依据
- 作为作品集或项目介绍时的产品说明底稿

---

## 2. 产品目标

### 2.1 一句话定位

`Aura 不是另一个通用聊天工具，也不是另一个纯笔记软件，而是一个面向长期项目推进的 AI 工作台。`

### 2.2 核心价值

Aura 要解决的问题，不是“用户能不能问 AI 一个问题”，而是：

- 用户在一个长期项目中产生的大量对话、想法、笔记、决策，是否能被持续沉淀
- 用户下一次回来时，AI 是否还能基于历史上下文继续推进
- 用户是否能把“聊天”转化为“项目资产”，而不是一次性消耗品

### 2.3 北极星目标

让用户在一个 workspace 中完成下面这条闭环：

`提出问题 -> 讨论方案 -> 形成结论 -> 保存为笔记 -> 生成待办 -> 下次继续推进`

### 2.4 产品亮点目标

Aura 的亮点不应建立在“模型比 ChatGPT 更强”上，而应建立在以下能力上：

1. `项目级记忆`
同一个 workspace 的对话、笔记、结论、待办能够持续积累。

2. `对话自动沉淀`
聊天结果不是停留在消息列表里，而是自动转化为摘要、结论、任务或笔记草稿。

3. `知识可回链`
AI 给出回答时，能够说明答案参考了哪些笔记、历史消息或项目结论。

4. `推进而非陪聊`
用户使用 Aura 的目的不是“问一个问题”，而是“把一件事情往前推进”。

### 2.5 首阶段目标用户

建议第一阶段聚焦两类用户，不要一开始做泛用产品：

1. `独立开发者`
用于产品构思、需求拆解、技术方案记录、版本复盘。

2. `自学者 / 学生`
用于学习计划、知识笔记、问题讨论、阶段总结。

---

## 3. 现状评估

基于当前代码结构，Aura 已经具备一个学习型全栈项目的基础框架，且已完成多个核心模块。

### 3.1 已有能力

#### 后端

- 用户注册、登录、JWT 鉴权
- 工作区 `workspace` 的增删改查
- 聊天消息存储与工作区绑定
- 笔记 `note` 的增删改查
- 模型配置 `model-config` 的增删改查
- 多模型接入基础能力
- 部分接口测试

#### 前端

- 登录 / 注册页面
- 聊天页
- 工作区列表与切换
- 笔记列表与编辑
- 模型配置页面
- Zustand 本地状态持久化
- 基础 API 调用封装

### 3.2 当前阶段判断

当前更接近：

`功能原型 + 学习项目 + 可演示的全栈雏形`

还没有达到：

`一个有清晰差异化定位、可持续使用、可稳定扩展的产品`

### 3.3 当前项目的优点

1. `业务模型已经搭起来了`
已经有 user、workspace、chat、note、model-config 这些明确实体，说明项目不是空壳。

2. `方向天然适合做 AI 工作台`
已有 workspace 和 note，这非常适合往“长期记忆”和“项目沉淀”方向发展。

3. `前后端边界比较清晰`
后续继续补能力时，不需要推翻整体结构。

### 3.4 当前项目的主要问题

1. `定位还不够聚焦`
现在更像“聊天 + 笔记 + 模型配置”的集合，还没有一个足够鲜明的产品主张。

2. `聊天和笔记之间缺少闭环`
两者都存在，但还没有形成“对话沉淀为项目资产”的核心链路。

3. `workspace 还是消息容器，不是项目容器`
现在工作区主要承载聊天，没有形成项目级状态、结论和上下文。

4. `工程化仍偏原型`
权限边界、错误处理、测试覆盖、稳定性、可维护性仍有明显短板。

---

## 4. 现状与目标的差距

这一部分最重要，它决定接下来应该先做什么，不该先做什么。

## 4.1 产品定位层面的差距

### 目标状态

用户能理解：

- Aura 是用来推进长期项目的
- Aura 会记住我的上下文
- Aura 能把聊天沉淀成笔记、结论和任务

### 当前状态

用户更可能理解为：

- 一个能聊天的小工具
- 一个带笔记功能的 AI 页面
- 一个可切模型的 demo

### 差距总结

`缺少明确的主叙事。`

目前功能不少，但没有一个“为什么必须用 Aura”的强理由。

## 4.2 核心体验层面的差距

### 目标状态

用户在一个 workspace 中可以：

- 围绕一个主题长期聊天
- 保存关键内容为笔记
- 自动得到总结和待办
- 下次继续时 AI 能理解之前发生过什么

### 当前状态

- 可以聊天
- 可以记笔记
- 但聊天和笔记关系较弱
- 没有自动总结、项目结论、任务提取、知识引用

### 差距总结

`缺少从“聊天”到“沉淀”再到“继续推进”的闭环。`

## 4.3 数据与记忆层面的差距

### 目标状态

AI 回答能够参考：

- 当前工作区历史对话
- 当前工作区内的笔记
- 历史总结
- 用户手动确认过的项目结论

### 当前状态

- 聊天消息有存储
- 笔记有独立存储
- 但没有面向回答阶段的统一记忆检索和注入机制

### 差距总结

`数据存在，但没有形成可用的项目记忆。`

## 4.4 工程质量层面的差距

### 目标状态

- 资源权限安全
- 接口行为一致
- 前端有基础路由保护与错误恢复
- 关键功能有测试
- 便于继续扩展

### 当前状态

- 已有基础鉴权
- 但仍存在资源级权限控制不足
- 测试覆盖有限
- 流式聊天、异常处理、状态一致性有待加强

### 差距总结

`现在足够学习和演示，但还不足以支撑较复杂的产品体验。`

## 5. 产品策略

## 5.1 不做什么

为了避免产品失焦，第一阶段不建议把目标放在以下方向：

1. `做通用大模型平台`
这会直接进入和 ChatGPT、豆包、通义等产品的正面竞争。

2. `做纯笔记工具`
这会进入和 Obsidian、Notion、语雀等产品的正面竞争。

3. `做很重的知识管理系统`
过早引入复杂的双链、插件体系、多人协作，会让项目失控。

## 5.2 第一阶段应该做什么

第一阶段只围绕一个核心命题：

`让 workspace 真正成为“项目工作台”，让聊天真正沉淀为“项目资产”。`

### 第一阶段核心功能主线

1. 项目工作区
2. 聊天沉淀
3. 项目记忆
4. 总结与待办

---

## 6. 任务拆解规划

下面按照优先级拆分为 4 个阶段。建议按顺序推进，不建议跳着做。

## 6.1 阶段 0：打底修整

### 阶段目标

让当前项目从“功能原型”进入“可稳定迭代”的状态。

### 优先级

`P0，必须先做`

### 任务清单

#### 任务 0.1：补齐产品文档和项目说明

目标：

- 明确产品定位
- 明确目标用户
- 明确模块边界

交付物：

- 产品规划文档
- README 启动说明
- 模块说明文档

验收标准：

- 新人能在 10 分钟内理解项目是做什么的
- 能在本地跑起来

#### 任务 0.2：梳理路由和页面结构

目标：

- 让页面结构与产品结构对齐

建议动作：

- 明确 `Chat / Note / Setting` 是否仍是一级导航
- 评估是否需要将 `workspace` 作为更核心的导航概念
- 统一页面标题、面包屑、布局语义

验收标准：

- 页面信息架构可自解释
- 用户能清楚知道自己当前在哪个项目、哪个模块

#### 任务 0.3：补齐基础权限控制

目标：

- 每个用户只能访问自己的数据

建议动作：

- 所有 `findById / update / delete` 增加用户归属校验
- note、workspace、model-config、chat 的单资源查询统一带 user 过滤
- 删除或访问越权资源时返回明确错误

验收标准：

- 不能通过直接改 id 访问他人资源
- 关键接口都有权限保护

#### 任务 0.4：统一错误处理与接口约定

目标：

- 让前后端能稳定对接

建议动作：

- 统一成功/失败结构
- 明确 HTTP 状态码语义
- 前端统一处理鉴权失败、表单错误、服务错误

验收标准：

- 前端不会因为后端结构不一致而写很多特判
- 登录失效时能统一跳转或提醒

#### 任务 0.5：补齐关键测试

目标：

- 让后续改动不容易把基础能力改坏

建议动作：

- 增加 note 接口测试
- 增加 chat 接口测试
- 增加 model-config 接口测试
- 增加权限边界测试

验收标准：

- 用户、工作区、笔记、聊天、模型配置都有最基本用例

---

## 6.2 阶段 1：做出产品主线

### 阶段目标

让 Aura 从“聊天 + 笔记”变成“项目工作台”。

### 优先级

`P0，最核心产品阶段`

### 任务清单

#### 任务 1.1：重新定义 workspace

目标：

- workspace 不再只是对话列表项，而是一个长期项目容器

建议新增字段：

- `description`
- `goal`
- `status`
- `summary`
- `lastActiveAt`

建议页面能力：

- 创建项目时填写项目名称、目标、默认模型
- 在项目页展示当前目标、最近总结、关联笔记数量、最近对话时间

验收标准：

- 用户看到 workspace 时会把它理解为“项目”，不是“会话”

#### 任务 1.2：支持对话转笔记

目标：

- 把聊天结果沉淀下来

建议页面能力：

- 在 AI 回复气泡上提供“保存为笔记”
- 支持选择保存为：
  - 完整回答
  - 选中片段
  - 自动摘要版

建议数据能力：

- note 与 chat 建立来源关联
- 记录来源消息 id、来源 workspace id

验收标准：

- 一段有价值的回复能在 2 步以内保存为笔记
- 保存后的笔记能追溯来源

#### 任务 1.3：自动生成会话总结

目标：

- 每轮或每次会话结束后生成可复用摘要

建议输出结构：

- 本轮讨论主题
- 主要结论
- 未解决问题
- 后续待办

建议实现方式：

- 在用户发送完成或会话结束后触发摘要生成
- 初版可以手动触发，后续再自动化

验收标准：

- 用户能快速回顾某个项目最近讨论了什么
- 下次继续时不必手动翻大量消息

#### 任务 1.4：项目待办提取

目标：

- 让 AI 不只提供信息，还帮助推动执行

建议页面能力：

- 从对话摘要中自动识别 TODO
- 支持用户确认、编辑、完成

建议数据结构：

- 增加 `todo` 或 `task` 实体
- 与 workspace 关联
- 可选关联 chat / note 来源

验收标准：

- 用户能从一段讨论直接得到可执行事项

#### 任务 1.5：项目首页视图

目标：

- 强化“项目工作台”感，而不是单纯消息流

建议展示区块：

- 项目目标
- 最新总结
- 今日待办
- 关联笔记
- 最近对话

验收标准：

- 用户进入 workspace 后，第一眼看到的是“项目状态”，而不是只有聊天输入框

---

## 6.3 阶段 2：做出核心差异化

### 阶段目标

让 Aura 真正具备“项目记忆”和“知识回链”能力。

### 优先级

`P1，决定产品是否出彩`

### 任务清单

#### 任务 2.1：项目记忆注入

目标：

- AI 回答时可以参考项目历史信息

第一版建议纳入的上下文：

- 最近 N 条聊天记录
- 最近 N 条笔记摘要
- 最近一次项目总结
- 当前项目目标

建议实现策略：

- 先做规则式拼装，不急着上向量数据库
- 按优先级和长度裁剪上下文

验收标准：

- 用户二次提问时，AI 能明显利用之前的上下文
- 不需要每次都重新解释背景

#### 任务 2.2：知识回链回答

目标：

- 提升回答可信度和可追踪性

建议页面能力：

- AI 回答底部显示“参考了哪些内容”
- 引用来源支持跳转到对应笔记或消息

建议实现方式：

- 初版由后端在上下文注入时携带 source metadata
- 返回时将来源映射到前端可展示结构

验收标准：

- 用户能知道这条回答参考了哪些已有资料

#### 任务 2.3：笔记与项目绑定

目标：

- 笔记不再是孤立内容，而是项目知识的一部分

建议动作：

- note 增加 workspaceId
- 支持查看“某个项目下的所有笔记”
- 支持从项目页直接创建笔记

验收标准：

- 用户能明确知道一条笔记属于哪个项目

#### 任务 2.4：结构化项目总结

目标：

- 建立长期项目记忆，而不是只保留原始文本

建议总结结构：

- 项目目标
- 当前进展
- 已确认结论
- 未决问题
- 下一步计划

建议机制：

- 每次更新总结都保留版本
- 支持人工编辑确认

验收标准：

- AI 和用户都能快速理解项目当前状态

---

## 6.4 阶段 3：提升完整度和展示力

### 阶段目标

让产品具备更好的体验、更强的可演示性和作品集价值。

### 优先级

`P1/P2`

### 任务清单

#### 任务 3.1：聊天体验增强

建议能力：

- 停止生成
- 重新生成
- 复制回答
- 多轮消息状态优化
- 更稳定的流式渲染

验收标准：

- 聊天过程更接近真实产品，而不是简单 demo

#### 任务 3.2：笔记体验增强

建议能力：

- 标签
- 搜索
- 按项目筛选
- 笔记摘要
- 笔记引用来源展示

验收标准：

- 笔记模块能真正承载沉淀内容

#### 任务 3.3：项目展示信息增强

建议能力：

- 项目封面 / 图标
- 项目状态标签
- 最近活跃时间
- 已完成任务数量

验收标准：

- workspace 列表更像项目看板，而非普通菜单

#### 任务 3.4：部署与演示能力

建议动作：

- 完善 `.env` 说明
- 补充初始化 SQL 和演示数据说明
- 添加 Docker 或本地一键启动说明
- 编写演示脚本

验收标准：

- 别人能更低成本地跑起来并理解产品价值

## 7. 建议的开发顺序

以下是建议的实际推进顺序。

## 7.1 第一优先级

1. 权限和接口规范修整
2. workspace 升级为项目容器
3. 对话转笔记
4. 会话总结

这四项完成后，产品主线会第一次真正成立。

## 7.2 第二优先级

1. 项目记忆注入
2. 项目笔记绑定
3. TODO 提取
4. 知识回链

这四项完成后，Aura 才会出现真正区别于通用聊天工具的亮点。

## 7.3 第三优先级

1. 聊天体验优化
2. 笔记体验优化
3. 视觉和展示优化
4. 部署和演示优化

这部分更偏“把产品做漂亮、做完整”。

目标：

- 权限、错误处理、测试补齐

- 可以稳定继续迭代，不容易一改就坏

## 8.2 里程碑 M2：形成产品主线

目标：

- workspace 项目化

成果判断：

- 用户第一次能感受到“这不是普通聊天工具”

## 8.3 里程碑 M3：形成差异化亮点

目标：

- 项目记忆注入
- TODO 提取
- 知识回链

成果判断：

- 产品有明确可讲述的独特价值

## 8.4 里程碑 M4：具备作品集表达力

目标：

- 体验打磨
- 演示流程清晰

## 9. 成功标准

如果 Aura 走对了方向，后续应当满足下面这些判断：

1. 用户不会把它只当成“另一个聊天页”
2. 用户会把 workspace 当成“正在推进的项目”
3. 用户会自然地把聊天结果保存、整理、复用
4. AI 回答会明显体现项目上下文
5. 用户下次回来能快速接着上次进度继续

---

## 10. 当前建议结论

Aura 最值得坚持的方向不是“做更强的模型入口”，而是：

`做一个能把长期项目中的对话、笔记、结论和待办串起来的 AI 工作台。`

因此，后续开发时应该始终用下面这个问题做判断：

`这个功能，是不是在帮助用户把项目继续推进，而不只是增加一个聊天或记录动作？`

如果答案是“是”，这个功能大概率值得做。

如果答案只是“看起来更像一个完整产品”，但不能增强项目推进闭环，就应降低优先级。
